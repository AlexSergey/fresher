# Security audit, 2026-11-25

The first security audit of Fresher, before the 0.1.0 release (plan [041](../plans/041-security-audit/readme.md)).
**This is an audit by AI agents, not a certification.** No third party reviewed the code, and an audit finds what its
readers thought to try. What it did not cover is listed below.

## Scope

The whole repository on the branch `feat/041-security-audit` (main as of 2026-11-25), against the
[threat model](./threat-model.md), in four areas:

- **Removal:** the cleaner, the cleanup journal, put back, the protected places, the Trash view.
- **Scan and parsing:** the walk, the modules' proofs, the property-list and small-file parsers, the external programs.
- **Shell and privacy:** the Tauri commands, capabilities and content policy, development-only code, the network.
- **Supply chain and build:** dependencies and lock files, the repository guards, CI, the bundle's signature.

## Method

1. **Attackers.** One agent per area, started fresh: it had the code, the restrictions and the threat model, not the
   plans' reasoning or the history of how the code was built. A finding had to be a reproduction (a failing test, a
   run, a measurement) or a precise reading of the code.
2. **An independent checker** reproduced each finding, set its severity (the checker's severity is the one below)
   and sharpened the fix direction. Nothing was refuted; four findings stayed "plausible" (reasoned, not run).
3. **Fixers** turned each proof into a test in the crate's normal layout, then made the root-cause fix, with the docs
   in the same commit. What was accepted became a known issue.
4. **A fix reader**, again fresh, read every fix commit. It found one new issue (NEW-1), two regressions of the fixes
   (Open Trash without Full Disk Access; a home reached through a link) and one residual described wrongly (SCAN-1);
   all four were fixed or written down before this report.
5. **The release bundle** was built once with `npm run build`, and its check passed (below).

Nothing ran against the user's real data: every attack ran on temporary trees and fakes.

### Residuals worth knowing

- **SCAN-1, check then run:** a look-alike bundle holding a copy of, or a link to, the genuine signed CLI passes the
  check and can be swapped before the run ([the known issue](../known-issues/app-docker-cli-checked-then-run.md)).
  Accepted for 0.1.0 by the user, 2026-11-25.
- **Docker:** the read runs the genuine CLI with `--host unix://<socket> --config /private/var/empty`, so the user's
  contexts, credential helpers, hooks and plugin folder are not read; plugin folders of the system (for example
  under `/usr/local`) are the CLI's own business and were not examined.
- **Open Trash** checks each name with `lstat` and then asks Finder; the folder could still change between the check
  and Finder's open. Finder only shows a folder; it launches nothing.

## The release bundle

`npm run build` on the branch, then its check (`scripts/check-bundle.ts`): the strict deep signature verifies, the
hardened runtime flag is set, there are no entitlements, the executable imports no socket, resolver or networking
call, and it holds no home path. It was not launched by the audit. The user checks by hand on that bundle:

- it starts;
- opening it a second time focuses the open window;
- Open Trash opens Finder, with and without Full Disk Access;
- put back from `~/.Trash` works;
- the Docker card still shows its numbers while the runtime (Docker Desktop or OrbStack) runs.

## Not covered

- **Removal:** the races of `remove/permanent.rs` and `guard/walk.rs` were read against their docs only (they have
  their own race tests); `remove/tool.rs`, the in-use and access guards and the uninstall path were not read;
  firmlinks, `/Volumes/Macintosh HD` as a root and `/var` against `/private/var` were reasoned, not run.
- **Scan:** no line-by-line review of `app-caches`, `jetbrains`, `xcode`, `logs`, `temp`, `downloads/unfinished`, the
  rescan through the change journal and the scan cache codec; the XML property-list reader was read, not fuzzed;
  the Docker CLI was never run, and no real app bundle was touched.
- **Shell:** the app was never run by an attacker, so the single-instance behaviour, what Finder does with a
  linked Trash and what the webview writes under `~/Library` are reasoned from source.
- **Supply chain:** `npm audit` (it needs the network); whether the pinned action commits match their tags; the
  GitHub repository's settings and branch protection.
- **Docker Desktop's signature:** its team was confirmed on its privileged helper, not on its CLI.

## How to report a problem

Privately, as [`.github/SECURITY.md`](../../.github/SECURITY.md) says: the repository's Security tab, "Report a
vulnerability". Do not open a public issue.
