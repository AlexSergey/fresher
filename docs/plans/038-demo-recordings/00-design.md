# 038 — Demo recordings: the design

**Status:** 🔨 in progress, awaiting the user's walk · **Version:** 0.1.0 · **Date:** 2026-11-22 ·
**Modules:** sandbox, testing, app, app/tauri, app/ui, scripts, fixtures, docs

Written on 2026-11-22 from the one-file draft and a fresh read of the code on `main` 33d51a6c (plan 034). Approved by
the user's delegation of 2026-11-22: build autonomously, the recommended decisions and agent's calls taken.

## Intent

The user's task (translated): "Think how to make a script that records a short video for the README, which can be
turned into a GIF for GitHub. It must be part of the application and be extended with scenarios."

A README without a moving picture of the app loses most visitors, and a recording made by hand is stale after the next
change and may show private paths. The recording must be a command: the same result every time, on made-up data.

## Goals

1. One command produces the README's animation and a video from the real app, with no hand on the mouse.
2. A scenario is a small file; adding a module's story is adding a file.
3. Nothing of the developer's Mac is in the picture, and nothing of this ships in a release build.
4. A scenario that no longer plays fails loudly, naming the step.

## Non-goals

- Recording in CI: capturing the screen needs a permission only a person's Mac has.
- Narration, zooms, titles, editing. A scenario is clicks and pauses.
- A mocked interface: the picture shows the real core on a real (generated) disk.
- The README's text and where the picture goes in it: plan [040](../040-readme/readme.md). This plan makes the picture.

## What the code has today (read on 33d51a6c)

- **Sandbox mode** (`app/tauri/src/sandbox.rs`, plan 007): `FRESHER_SANDBOX=<abs folder>` moves the whole debug build
  into a sandbox folder. Its world (`world.toml`) gives the clock (`StartedClock::at(world.now)`), the running apps,
  the access, the installs and stated facts read through `FactsLens`. The volume is the Mac's (`MacVolumes`).
- **The generator** (`crates/sandbox`, `fresher-sandbox generate <feature|all> [--into <dir>]`) writes case files
  (`fixtures/sandboxes/<feature>.toml`) with `now = SystemTime::now()`. A case is `negative` or `positive`; a positive
  needs an `expect`.
- **Sizes**: the app shows the space a file takes on disk (`Sizes::allocated`; `docs/testing.md`, "Sandboxes": "a
  sparse file none"). A sparse file of the case files shows **0 bytes**. The draft's "tens of gigabytes that cost no
  disk" does not hold without a change (section 1).
- **Paths** are shown whole (`PathText`), not as `~/…`: a sandbox under the developer's home shows the user's name.
- **The IPC types** are generated by `ts-rs` (`app/tauri/tests/bindings.rs` → `bindings.generated.ts`); `ts-rs` is a
  workspace dependency used by `fresher-core`.
- **The shell** registers commands in `generate_handler!`, which takes `#[cfg(...)]` on a command (tauri-macros 2.7.4,
  read in its source); every command is classified as an action or a read in `app/tauri/src/dev_runs/commands.rs`.
- **The staged-files guard** (`scripts/check-staged.ts`) refuses any file over 1 MiB, with one listed exception.
- **The window**: 1100 × 720 logical, minimum 900 × 600, transparent with the sidebar effect (`tauri.conf.json`).

## Design

Three parts, each reusing what exists.

### 1. The demo world

A **demo world** is `fixtures/demos/<world>.toml`, a file in the case-file format with a `[demo]` header, written by
the same generator. Unlike a test's case file it is a believable Mac: several modules at once, realistic names and
sizes, its own clock and its own volume.

```toml
feature = "developer-mac"

[demo]
now = 1795000000                       # the world's clock, seconds since the Unix epoch: fixed, never the wall clock
sizes = "as-declared"                  # every sparse file takes its declared size on disk, stated (see below)
shows = ["dev-caches.xcode-derived-data", "app-caches.library-caches"]  # categories the world must offer
[demo.volume]
name = "Macintosh HD"
capacity = 494384795648
used = 401234567890
free = 93150227758

[[case]]
name = "Xcode's build products of three projects"
kind = "scenery"
[[case.file]]
path = "home/Library/Developer/Xcode/DerivedData/Atlas-bxkqzr/Build/Products/Debug/Atlas.app/Atlas"
size = 6442450944
age = "40d"
```

- **`kind = "scenery"`**, a third case kind: a part of a demo world; nothing it shows is checked by the autotest. A
  demo file has only scenery cases and no `module`; a scenery case has no `expect`, `map` or `left-out`; a scenery
  case outside a demo file is refused, and so is a negative or positive case inside one.
- **The clock**: `now` replaces the generation moment, so dates and ages in the picture never change between
  recordings.
- **Sizes**: with `sizes = "as-declared"` the generator states, for every sparse file of the world, an allocated size
  equal to its declared size: a new stated fact `allocated` in `world.toml`'s `[[entry]]` and in `Stated`
  (`crates/testing`), which `FactsLens` reports instead of the disk's. Gigabytes cost no disk and show as gigabytes.
  The cleaner reads the disk, as for every stated fact.
- **The volume**: `[demo.volume]` is written into `world.toml`; sandbox mode answers `Volumes::space` with it (a
  wrapper over the Mac's volumes, `StatedSpace`, in `crates/sandbox`) and leaves `identify` and `available` to the
  Mac. The ring and the storage map show the world's disk, never the developer's.
- **`shows`**: the categories the world must offer. A Rust test scans every demo world in sandbox mode with every
  module and fails when one of them offers nothing: a world that silently stops showing a module fails in CI, not in
  front of the camera.
- **Where it is generated**: `fresher-sandbox demo <scenario> [--into <dir>]` writes the scenario's world into
  `/private/tmp/fresher-demo/<scenario>-<n>` by default (the first `n` not taken): a path with no user name in it. The
  folder is new on every run: nothing is removed or overwritten (only the cleaner deletes), an existing `--into` folder
  is refused, and old demo folders stay until macOS clears `/private/tmp`. The generator also takes a world (or any
  case file) by path:
  `fresher-sandbox generate <feature|all|path.toml> [--into <dir>]`, so `npm run dev:sandbox` can show a world by hand.

### 2. The scenario and the player

A **scenario** is `fixtures/demos/scenarios/<name>.toml`: its world, the window size, and steps from a closed list.

```toml
world = "developer-mac"
window = { width = 1100, height = 720 }

[[step]]
click = { role = "button", name = "Scan" }
[[step]]
wait = "scan-finished"
[[step]]
pause = 1200
[[step]]
hover = { role = "button", name-start = "Developer caches" }
[[step]]
scroll = { role = "region", name = "Results", by = 480 }
[[step]]
wait = { role = "heading", name = "Cleanups" }
```

- **Steps**: `click`, `hover`, `scroll` (a target and `by`, pixels, not 0), `wait` and `pause` (1 to 10 000 ms).
  Exactly one key per step.
- **A target** is an accessible role and name, as the e2e tests address elements: `role` from a closed list (`button`,
  `link`, `tab`, `checkbox`, `switch`, `heading`, `region`, `dialog`, `row`) and either `name` (the whole accessible
  name) or `name-start` (its start, for a name that carries a size). A renamed button breaks the scenario, never
  silently the picture.
- **A wait** is a named state of the app (`scan-finished`, `cleanup-finished`) or a target that appears.
- **Parsed in Rust** (`crates/sandbox/src/scenario.rs`): typed (`Scenario`, `Step`, `Target`, `Role`, `NameMatch`,
  `Wait`, `AppState`), refused with a typed error naming the step, and exported to TypeScript with `ts-rs` beside the
  core's types, so the UI receives typed steps through the one IPC module. The window is 900–1600 × 600–1000 logical;
  the pauses of a scenario add up to at most 20 s (the budget's length).

**The shell's demo mode** (`app/tauri/src/demo.rs`, debug builds only, beside sandbox mode): `FRESHER_DEMO=<absolute
path of a scenario>` with `FRESHER_SANDBOX` set (refused without it, refused when relative or not valid, the start
failure's message naming why). The shell sizes the window to the scenario and places it at the logical point (80, 80)
of the main screen. Two commands, registered under `#[cfg(debug_assertions)]`:

- `demo_play` (a read) → `Option<DemoPlay>`: `None` outside demo mode; else the scenario and the private texts the
  picture must never contain (the real home folder's path and the sandbox folder's path). On this call — the UI is
  drawn — the shell writes `<sandbox>/demo-window.json`: the window's content rectangle on its screen in physical
  pixels and the scale factor, for the recorder.
- `demo_finished(outcome)` (an action) → writes `<sandbox>/demo-result.json` (`finished` with the elapsed
  milliseconds, or `failed` with the step's number and the reason) and ends the app with 0 or 1.

**The UI's player** (`app/ui/src/demo/`): a lazy chunk imported only under `import.meta.env.DEV` in `main.tsx`, so the
release bundle has none of it. It asks `demoPlay()`; with a scenario it marks the page (`data-demo="playing"`, which
hides the build banner), waits a lead-in of 1500 ms, then plays each step on the real interface with a drawn pointer
that glides to each target (600 ms) and presses. A target must match exactly one visible element within 5 s; a named
state within 60 s. After each step the page's text is checked for the private texts. It reports `finished` (with the
elapsed time) or `failed at step N: <reason>` through `demoFinished`.

### 3. The recorder

`scripts/demo-record.ts`: `npm run demo:record -- <scenario|all>` and `npm run demo:check -- <scenario|all>` (the
same script with `--check`). For each scenario, in name order for `all`, stopping at the first failure:

1. `cargo run -q -p fresher-sandbox --locked -- demo <scenario>`: the world in a new folder,
   `/private/tmp/fresher-demo/<scenario>-<n>`, read from its output line.
2. `npm run dev` with `FRESHER_SANDBOX=<that folder>` and `FRESHER_DEMO=<repo>/fixtures/demos/scenarios/<scenario>.toml`.
3. **Record only**: once `demo-window.json` appears, capture the main screen with `ffmpeg` (`avfoundation`, no cursor,
   30 frames a second, lossless) into `NO_COMMIT/demo/tmp/`, until the app ends; stopped by `q` on its input.
4. Read `demo-result.json`: none, or `failed`, fails the run naming the step and the reason; a run longer than the
   budget's 20 s fails too. A timeout of 120 s from the window's file ends a hung run.
5. **Record only**: encode with `ffmpeg`: the window's rectangle cropped and the lead-in trimmed into
   `NO_COMMIT/demo/<scenario>.mp4` (H.264, full resolution, out of git), and `assets/demo/<scenario>.gif` through a
   two-pass palette: 800 px wide, 12 frames a second. A GIF over 5 MiB is refused and not written.

`demo:check` plays without capturing: no permission needed. It runs before a release and whenever a scenario or a
screen it touches changes. The recorder's command plan is unit tested with a fake spawner, as `sandbox-dev.test.ts`.

**The GIF in git**: `assets/demo/*.gif` is allowed up to 5 MiB by the staged-files guard (its own limit, recorded in
`docs/hacks/`); `.gitattributes` marks `*.gif` binary. The video stays in `NO_COMMIT/`.

### 4. The first scenarios

- `overview` (the README's hero): scan, the result's danger zones, a category's details.
- `cleanup`: select, review, confirm to the Trash, the result, Cleanups, put back.

Both touch only screens on `main` today. The screens of plans 031, 032, 035, 036 and 037 (merged before this plan is
built) get scenarios when they are wanted: a new file each, no code. Plan 039's wording changes may rename targets:
`demo:check` names the step that broke.

## Testing

- **Rust**, negatives first: the demo header and scenery kind (each refusal, then a world parsed and generated with
  its clock, stated sizes and volume); `Stated.allocated` through `FactsLens`; `StatedSpace`; the scenario's every
  refusal, then the shipped scenarios; `fresher-sandbox demo`'s new folder (two runs make two folders, an existing
  folder is refused and untouched, nothing is deleted); the shell's demo mode (refusals, `demo_play` without demo
  mode is `None`, the two files);
  every demo world scanned in sandbox mode offers each of its `shows`.
- **UI** (Vitest), negatives first: the finder (no match, two matches, a hidden element, a role of the wrong kind), the
  steps (a target that never appears, a state that times out, a private text on the page), the player's outcome, the
  start doing nothing without a demo.
- **Scripts** (`node --test`): argument parsing, the command plan for check and record, the encoding commands, the
  result file's reading, the budget.
- **By hand** (the user): `npm run demo:check -- all`, then `npm run demo:record -- overview` once the terminal has the
  screen recording permission.

## Agent's calls (to check)

1. **The real app in sandbox mode is recorded**, not the mocked interface in a test browser: the picture is the
   product, with the native window. Cost: a person's Mac and the screen recording permission.
2. **The player is inside the app, debug builds only**; no outside tool clicks the window.
3. **Scenarios are data** (a closed list of steps), parsed and typed in Rust, sent to the UI as generated types.
4. **The GIF is committed, the video is not**; the staged-files guard allows `assets/demo/*.gif` up to 5 MiB (the
   one-MiB rule stays for everything else). Cost if wrong: a few megabytes of history per re-recording; the other way
   is a GIF hosted as a release asset, which plan 040 can take.
5. **The build banner is hidden while a demo plays**; the README says the picture shows generated sample data (plan
   040).
6. **`ffmpeg` only**, as a development tool on the developer's Mac (GPL build, never shipped); no second encoder until
   the picture's quality asks for one.
7. **Capture with `ffmpeg`'s `avfoundation`, the whole main screen, cropped afterwards** (rather than `screencapture
   -v`, which needs the rectangle before the window exists and stops by a time limit). Unverified on macOS 27: if it
   fails, the capture command is one function of the recorder to switch to `screencapture`.
8. **A new stated fact `allocated`** (in `crates/testing` and `world.toml`), written only by a demo world, rather than
   real bytes (64 MiB a file, 512 MiB a world: a picture of megabytes). Not a core change: `FactsLens` and the world
   are development code.
9. **A stated volume for a demo world** (`StatedSpace`), so the ring never shows the developer's disk. The build
   banner does not name it (that is `Simulated`, a core type): the banner is hidden while recording anyway.
10. **The world is generated in a new `/private/tmp/fresher-demo/<scenario>-<n>`** on every run, a path with no user
    name; nothing is removed (the controller's ruling of 2026-11-22: only the cleaner deletes, no second deletion
    point); old folders stay until macOS clears `/private/tmp`.
11. **The private texts check**: the player fails when the page's text contains the real home's or the sandbox's
    path; the user's name alone is not checked (it may be a common word).
12. **Two files at the sandbox's root** (`demo-window.json`, `demo-result.json`) are the shell's only channel to the
    recorder, rather than the app's exit code through `tauri dev` (not known to pass it on) or its output.
13. **The two demo commands live in the one IPC module** (`app/ui/src/ipc/index.ts`), as the rules ask; their two
    names are in the release bundle's command table, unused (the shell of a release build has no such command).
14. **The window is placed at (80, 80) of the main screen**, with its vibrancy kept: the blurred wallpaper shows
    through the sidebar (the walk asks for a plain wallpaper).
15. **Budget**: 800 px wide, 12 frames a second, at most 20 s and 5 MiB; the length is checked by `demo:check` too
    (the player's elapsed time), so a scenario over budget fails before any recording.

## Conclusions

Built as designed, 🔨 awaiting the user's walk (the plan's summary is in [`readme.md`](./readme.md)). What changed from
the design and why:

- Call 10 became a ruling: a new folder per run, nothing removed, because only the cleaner deletes.
- The player refuses the permanent delete, `Delete` and `Remove` at run time (prefix match), and the scenario test
  traces every target to a text.
- `capabilities/default.json` and `build.rs` list `demo_play` and `demo_finished` in every build; only the handler is
  debug-only.
- The recorder starts the app in its own process group and stops the group on every exit path.
- Not verified, as the design said: `avfoundation` on macOS 27 and the crop of the window.
