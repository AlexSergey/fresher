# 034/02/03 — The UI

**Status:** ✔️ done · **Version:** 0.1.0 · **Date:** 2026-11-22 · **Modules:** app/ui, docs

The interface's path for the two new categories: their cards on Scan, their Details with findings titled by browser,
profile and folder, the review, a cleanup that empties, an open browser's left-out. No new component: titles, reasons
and category texts are the core's, the emptied outcome is shown since plan 008. The design:
[`../00-design.md`](../00-design.md), section 7.

## Context for the implementer

- Read `app/ui/src/test/app-caches-scan.ts`, the `appCaches` script and `appCachesCleanup` in `app/ui/e2e/core-mock.ts`,
  the app-caches scenarios in `app/ui/e2e/flows.spec.ts` (around "selecting app caches makes the review name Low"),
  and the `appCaches` rows of `visual.spec.ts` and `axe.spec.ts`. Follow them.
- Rules: TypeScript strict, no `any`, `type` over `interface`, readonly; components never call `invoke`; the UI renders
  what the core sends. A mock states only what the core can produce together: an item is offered or left out, never
  both; a left-out is in one of the module's categories.
- The module now declares three categories (`app-caches.library-caches`, `app-caches.browsers`,
  `app-caches.web-engine`), all Low, in that order: the module info of every app-caches mock says so.

## Files

- `app/ui/src/test/app-caches-scan.ts` — the module info lists the three categories (with their texts from
  `modules/app-caches/locales/en.json`); export the small builders the new scan reuses (`sized`, `text`, the finding
  builder generalised to a path, a category and a title) rather than copying them. If the existing app-caches
  screenshots change, they are updated and looked at.
- `app/ui/src/test/app-caches-browsers-scan.ts` (new) — a scan as the core streams it: `app-caches.browsers` with
  `Google Chrome, Default: Cache` (400 MB), `Google Chrome, Default: Code Cache` (150 MB), `Google Chrome, Profile 1:
  Cache` (90 MB) — each `title.profile` with `app`, `profile`, `folder`, reason `app-caches.reason`, app
  `com.google.Chrome`, removal `emptyFolder`; `app-caches.web-engine` with `Redis Insight: Cache` (20 MB) and
  `Redis Insight: GPUCache` (5 MB) — `title.part`; one left-out `app-caches.left-out.app-open` in
  `app-caches.browsers` (Firefox's `cache2`, 30 MB). Paths under `/Users/someone/Library/...`. Its dictionary exported
  for the specs.
- `app/ui/e2e/core-mock.ts` — the script `appCachesBrowsers` (scan, overview, answers, ignoring, a cleanup answering

- `app/ui/e2e/flows.spec.ts` — the scenarios, negatives first:
  - negative: "an open browser's cache cannot be selected";

    itself stays.").
- `app/ui/e2e/visual.spec.ts`, `axe.spec.ts` — the Details of `app-caches.browsers` (findings and left-out line) and of

- `app/ui/e2e/screenshots/` — the new images (and any changed ones), looked at before committing.
- `docs/testing.md` — `src/test/app-caches-browsers-scan.ts` beside the `app-caches-scan.ts` sentence.

## Conclusions

Built as the step says: the mock scan (`app-caches-browsers-scan.ts`) states what the core produces together (the three
categories of the module, Chrome and Chromium folders titled by browser, profile and folder, Redis Insight's by app and
folder, an open browser's left-out), the flows, visual and axe specs, and four new baselines (browsers and web-engine,
chromium and webkit), each looked at. The existing `app-caches` baselines are unchanged and axe is clean. `npx vitest
run`: 1160 tests, UI coverage 97.76 % of lines; `npm run test:e2e:ui`: 552 passed, plus one webkit hover flake in
`scan.spec` that passed on rerun.

Change from the step: the cleanup mock empties `Cache` (moved 4) and `Code Cache` (moved 0), so the row "Emptied. The
folder itself stays." is tested; a detail row shows the folder's basename, and the tests filter on it.
